# From Regime Shift to Redundancy: Boundary Conditions for Swarm-Based Feature Selection

Code and results for a study of when wrapper feature selection beats simply
using all features. We extend OrPSOC to non-stationary data and evaluate it,
alongside other swarm and non-swarm selectors, on synthetic, financial and IID
benchmarks under one walk-forward protocol.

This is release v1.0.0, the frozen version that accompanies the paper.

## Repository layout

```
orpsoc/          core library: OrPSOC and its adaptive variants, walk-forward CV,
                 fitness, detector, checkpointing and run provenance
data_prep/       builds every dataset from its public source (see data/README.md)
pipeline/        the core ablation at D = 50
  step7_ablation.py    synthetic benchmark, five conditions, 30 seeds
  step8_results.py     statistics for the synthetic ablation
  step9_real_data.py   sector ETFs and Fama–French, five conditions, 20 seeds
experiments/     follow-up studies, one script per question
  adaptation/      warm start, population memory, APSOLL trigger, real-market
                   adaptation, subset sizing, selection stability
  detector/        regime-change detectors judged against a noise null
  dimensionality/  the width ladder and synthetic sweep, external comparators,
                   sparse-PSO correction, IID benchmarks, collinearity
    theta_sweep/   fitness-weight sweep (Supplementary Table S13), as run
  penalty/         ridge sweep and nested cross-validation of the penalty C
analysis/        renders every table and figure from results/ (no re-running)
results/         stored outputs of the runs reported in the paper (JSON)
tables/          LaTeX tables generated by analysis/
tests/           correctness checks for the evaluation engine
```

Generated figures go to `figures/` (vector PDF, manuscript file names) and
`plots/` (PNG previews). Neither is committed; `analysis/` recreates them in
minutes.

## Installation

Python 3.12 (the paper's results were produced on 3.12.3) or 3.13:

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

`requirements.txt` pins every direct dependency exactly. `environment-lock.txt`
is the full `pip freeze` of the c7a.2xlarge environment that produced the later
results (see "Computing environment").

Scripts are run from the repository root (`python pipeline/step7_ablation.py`);
each one sets up its own import path, so no package install is needed.

### Path A: regenerate every table and figure from the stored results (about a minute)

No datasets needed. **One command**, with the Zenodo archives downloaded into a
folder (it unpacks them in the right order, rebuilds the merged ladder and runs
every renderer below, then lists any file that differs from the committed one;
about 20 s on an Apple M4):

```bash
bash scripts/rebuild_from_deposit.sh /path/to/zenodo/files
```

Without the archives, run the renderers one by one. They use the committed
merged ladder; Fig. S4 is skipped and Table 8a is left out (both need the
archives):

```bash
python analysis/ladder_tables.py            # Tables 6, 7, 8b, S2, S4
python analysis/ridge_tables.py             # Table S6
python experiments/penalty/nested_cv_stored.py --table-only   # Table 9
python analysis/fitness_tables.py           # Table 12 fitness column, Fig. S10
python analysis/golub_tables.py             # Table S9
python experiments/adaptation/crossseed_jaccard.py            # Table S11
python analysis/make_manuscript_figures.py  # Figs 3, 5, S2, S5, S6, S7
python analysis/nested_cv_figure_ref.py     # Fig. 4
python analysis/make_supplementary_figures.py   # Figs S1, S3, S8, S9 (+ S4 with checkpoints.tgz)
git status --short tables/ results/         # should print nothing
```

On a clean checkout every regenerated table is byte-identical to the committed
one, so `git status` stays clean. A few of these scripts also rewrite the
stored JSON they summarise (`results/arm_pairwise.json`,
`results/crossseed_jaccard.json`), with identical bytes.

`analysis/nested_cv_tables.py` is **legacy**: it renders the superseded
re-swarm nested CV (not in the paper) and exits 1 by design, because its RFE
predates the 2026-11-12 re-pin (see Table 9 above). Table S5 needs the datasets.

### Path B: re-run the experiments (hours to weeks of compute)

This needs the datasets (see [Data](#data)). Run the engine checks first:

```bash
python tests/test_equivalence.py     # engine correctness checks (~10 s)
python pipeline/step7_ablation.py    # -> results/step7_ablation_v2.json
python pipeline/step8_results.py     # -> results/step8_statistical_summary.json
python pipeline/step9_real_data.py   # -> results/step9_real_data.json
python experiments/<study>/<script>.py
```

Each experiment script states at the top the question it answers, what it reads
and what it writes. Every long-running script checkpoints each (dataset, seed,
configuration) unit under `results/checkpoints/`, keyed by a hash of its
configuration and of its own source plus `orpsoc/utils.py`. Interrupted runs
resume, and changed code never reuses stale units. Seeds run in parallel
(default: cores − 2, at most 6); set `ORPSOC_N_JOBS` to override.

Compute. One dense binary-PSO search (20 particles × 60 iterations, before the
sparsity correction) was timed per walk-forward fold on one core of the
c6i.8xlarge. These are upper bounds for the sparsity-corrected searches the
paper uses:

|---|---|---|---|---|
| synthetic `hd_*` | 50 / 200 / 500 / 1000 / 2000 | 58 / 185 / 469 / 1,011 / 1,914 s | 0.4–14 s | under 1 s |
| Fama–French factors | 50 | 96 s | 0.8 s | under 0.1 s |
| `ff49ind` / `ff100` | 491 / 951 | 1,182 / 2,228 s | 8 / 16 s | under 3.1 s |

#### The θ sweep (Table S13)

```bash
DEADLINE_MIN=0 ROOT=$PWD PY=python \
TOOLS=experiments/dimensionality/theta_sweep \
```

### Two copies of the input data

The Ken French industry files were downloaded twice: on 2026-08-26 (the
canonical copy, on the c7a) and on 2026-09-06 (the laptop copy). They differ
in about 1% of cells ([`data/README.md`](data/README.md);
`data/CHECKSUMS.sha256` lists both). Every Apple-silicon result on the
industry data that could be checked used the laptop copy: the ladder RFE arm
and the penalty study. The previous ind5 LogReg and LightGBM records also used
the laptop copy; their platform is UNKNOWN (at ind5 the all-features arm gives
the same bits on Apple silicon and the c7a, and their units sit in the c7a's
own checkpoint store).

That data-copy difference is why the RFE arm, the
ind5 LogReg and LightGBM records and the penalty study were re-run on the c7a
with the canonical copy on 2026-11-12/13. What replaces what was fixed before
the runs: the re-run values are the record whatever they show, and no cell
mixes the two copies. No cell changed sign or significance except one (linear
SVM, RFE, p = 171: +0.0059 to −0.0392\*). The values they replace are kept:
`results/tier_d_ladder_rfe_superseded.json` holds both RFE versions for the
300 re-pinned records, and the previous ind5, `swarm_fitness.json` and
`nested_cv_stored.json` are in the git history (commit `bb8e31a`).

Still on the laptop copy: the ridge sweep (Table S6), which was not re-run,
the data statistics of Table S5 (same at printed precision on either copy), and
`nested_cv_c.json` (not in the paper). The market datasets (sector ETFs,
Fama–French factors, bonds, commodities, `v2_regime_switch`) exist only as
laptop builds; the c7a check reruns of `pareto_knee` (Table S10) and
`adapt_4markets` ("46 of 48") used them and reproduced the paper's numbers.

### Does the platform change the numbers?

For the adaptation study and the regime detectors, no: re-running units on
Apple silicon (the APSOLL patience-and-rearm sweep, elite fraction, lag
factorial, gated memory, all four detector files) gave the same bits as the
stored results, and the APSOLL sweep is known to come from the c6i.

For the real ladder, slightly: Apple silicon and x86-64 differ in the fourth
decimal or beyond (3.8 × 10⁻⁴ per fold on the ind10 LogReg all-features arm,
up to 3.7 × 10⁻² on LightGBM), while the two x86 instances agree to
5 × 10⁻¹¹. On the same data copy (ind10–ind17), the all-features cell means
of Apple silicon and the c7a differ by at most about 4 × 10⁻⁴. RFE is the
exception; see
[Known reproducibility limitation: RFE](#known-reproducibility-limitation-rfe).

The platform could not be determined for `golub_reconcile.json` (Section
3.7.1, Table S9), `warm_gate.json` or `tier_d_ksweep.json`; the last two are
not used in the paper. `pareto_knee.json` (Section 3.2.1, Table S10) and the
four detector files are probably from the c6i, but this is unverified.
`compass_ceiling.json` is the Apple-silicon version. A c6i rerun differs only
in its sector-ETF blocks (cause UNKNOWN: platform or raw-data copy). The
regime-switch numbers the paper reports (ceiling +0.718, criterion +0.201,
55%) are identical in both versions.

### Code provenance

Each stored result records a SHA-1 of the source files that produced it. Those
runs used the pre-release file layout (for example `orpsoc_utils.py`, now
`orpsoc/utils.py`), so the recorded hashes do not match the files in this
repository. The check below was run on 2026-11-12 to confirm that the release
code is the code that produced the stored results:

- **Every recorded hash was located.** The engine and pipeline versions behind
  the D = 50 results are in the public development repository
  `kritgun-1907/orpsoc_project`: `orpsoc_utils.py` `03133f03…`,
  `step7_ablation.py` `bdca7591…` and `step9_real_data.py` `39d80d2d…` at commit
  `a477edd2` (2026-08-07), and `orpsoc_utils.py` `8a019318…` at `712939ce`
  (2026-08-08). The four adaptation scripts with recorded hashes match the
  copies kept on the c7a.2xlarge exactly.
- **The differences to this release were reviewed line by line.** They are
  import paths, file paths and comments; parameters added with defaults that
  reproduce the old behaviour (`init_density=None`, `transfer_bias=0.0`,
  `density=None`, `switch_pair=None`); extra output fields; and a checkpoint
  file-name shim that applies only on Windows. step7 now passes the true switch
  pair to the Jaccard split, which is the same pair as the old midpoint for the
  paper's configuration (8 folds, break at row 500). The one behaviour change
  is that `elite_frac = 0` now means zero elites rather than one. It affects
  only the `0.0` arm of `results/elite_frac_sweep.json`, which the paper does
  not report (the paper fixes the elite fraction at 0.2).
- **Same machine, two code versions.** On the c7a.2xlarge, this release and the
  development code kept there produced bit-identical output for every arm,
  RFE included (ind17, LogReg, θ = 0.5, seeds 0–1).
- **Release code against the stored paper values.** In the same run, all
  features, sparse PSO, mRMR and LASSO matched the stored values to within
  5 × 10⁻¹¹ with identical subset sizes. RFE did not (see the next section).
  `tests/test_equivalence.py` passes with this release.

## Known reproducibility limitation: RFE

RFE is deterministic within one environment: re-running identical units gives
identical AUCs. It is not numerically portable:

> RFE is not numerically portable: with identical code, scikit-learn 1.8.0 and
> identical per-fold budgets, its cell-level ΔAUC moves by up to 0.056 between
> Apple silicon and x86, and by up to 0.068 between two downloads of the same
> Ken French files (which the source revises). Every other arm reproduces across
> platforms. The RFE values reported come from a single platform and data copy
> (x86 c7a, download of 2026-08-26).

The evidence is three runs of the same 180 RFE units (ind10–ind17 × LogReg,
LightGBM, k-NN × 20 seeds), all with this release's code, scikit-learn 1.8.0
and the stored sparse-PSO budgets: Apple silicon on the laptop data copy (the
previously published values), Apple silicon on the canonical copy, and the c7a
on the canonical copy. No record is bit-identical between any two of them. Per
cell, changing only the data copy moves ΔAUC by −0.001 to +0.068; changing
only the platform moves it by −0.005 to −0.056. The two effects are of similar
size and often of opposite sign. For the same reason RFE is left out of Table
S13.

**The values of record.** Every RFE value in the ladder that the paper uses
now comes from the c7a, scikit-learn 1.8.0, the canonical data copy and the
stored sparse-PSO budget of the same record (asserted per record):

- `rfe_repin.py`, 2026-11-12: ind10–ind30 × LogReg, LightGBM, k-NN (240
  records) and LinearSVM (80), and ind5 k-NN (20). LinearSVM ind30 and ind5
  k-NN reproduced the previous values bit for bit; the other 300 records
  changed.
- ind5 LogReg and LightGBM (40 records): every arm re-run together on
  2026-11-12/13, so RFE and the other arms share one data copy.

Before the re-pin, 49 of the 240 main-ladder records had used an RFE budget
that differed from the stored sparse-PSO budget in one to three folds (those
budgets came from the Apple-silicon swarm on the laptop copy). That is why
Table 12 showed RFE k = 11.1 against sparse PSO's 11.0 at p = 301. It now
shows 11.0. The budget mismatch explains little of the change: in the 191
records whose budgets already matched, no record is bit-identical to the
re-pin either.

`results/tier_d_ladder_rfe_superseded.json` holds, for each of the 300 changed
records, the previous and the current RFE arm, the stored budget and whether
the previous budget matched it. No script reads it.

To regenerate the RFE arm (x86-64, the canonical data copy, `checkpoints.tgz`
from the Zenodo deposit), make the stored budgets visible under this release's
provenance generation (its hash differs from the original because file names
changed) and re-run:

```bash
G=results/checkpoints/tier_d_fullnovelty
mkdir -p $G/aad95a66b882 && cp -p $G/29a57cced36f/*.pkl $G/aad95a66b882/
RP_DATASETS=ind10,ind12,ind17,ind30 RP_MODELS=LogReg,LightGBM,kNN,LinearSVM RP_SEEDS=20 \
  python experiments/dimensionality/rfe_repin.py
RP_DATASETS=ind5 RP_MODELS=kNN RP_SEEDS=20 python experiments/dimensionality/rfe_repin.py
```

On another platform or data copy, expect differences of the size above.
`ladder_penalty_c7a_box_20261113.tgz` in the Zenodo deposit holds the units
of record, so the committed ladder rebuilds without re-running anything
(`scripts/rebuild_from_deposit.sh`).

## Data

No dataset is redistributed here. Every dataset is rebuilt from its public
source by the scripts in `data_prep/` (and `pipeline/step9_real_data.py`):

- **Kenneth R. French Data Library**
  (`https://mba.tuck.dartmouth.edu/pages/faculty/ken.french/ftp/`): the
  Fama–French five-factor daily file, the 5- to 49-industry daily portfolio
  files and the 100 size/book-to-market portfolios, from 2000-01-01.
- **Yahoo Finance**, downloaded with the `yfinance` package
  (`yf.download(..., auto_adjust=True)` in `pipeline/step9_real_data.py` and
  `data_prep/build_extra_markets.py`): nine SPDR sector ETFs from 2000-01-01,
  six bond ETFs from 2003-01-01 and six commodity ETFs from 2007-01-01.
- **OpenML** (`sklearn.datasets.fetch_openml`): `madelon` (data id 1485) and
  `leukemia` (data id 1104, the Golub et al. 1999 data, called `golub` here).
- **Synthetic** benchmarks, generated with fixed seeds by
  `data_prep/make_benchmark_v1.py`, `make_level0_null.py`,
  `make_benchmark_v2.py` and `make_highdim_sweep.py`.

[`data/README.md`](data/README.md) gives the build order, the exact command
for each dataset, the file and ticker lists, and each source's terms.
`python data_prep/verify_data.py` checks every dataset before a run.
Yahoo Finance and the Ken French library revise past values, so a fresh
download can differ slightly from the series the stored results used. The
original downloads date from 2026 (details in `data/README.md`): sector-ETF
prices and the Fama–French factors on 2026-06-14, bond and commodity ETF prices
on 2026-08-06, the Ken French industry portfolios on 2026-08-26, and madelon and
golub on 2026-08-25.

## Protocol notes

- Walk-forward cross-validation with eight folds and a gap equal to the label
  horizon; the inner PSO validation split is taken from the training window
  only, so the test fold is never seen during selection.
- On the real datasets run with a 150-row first training window, fold 0 holds a
  single class and cannot be scored; it is stored as AUC 0.5 for every arm and
  the baseline alike. Every table and figure averages the seven scoreable folds
  (`analysis/folds.py`); synthetic data keeps all eight.
- Fixed seeds throughout: 30 for the synthetic ablation, 20 for the real-data
  ablation and the width studies. Paired comparisons use Wilcoxon signed-rank
  tests.
